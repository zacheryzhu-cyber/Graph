Hands-on lab report · semiconductor fab facilities · Nov 2026

Three graphs, one fab

The same fab utility network was built as plain RDF, as RDF 1.2 (the successor to RDF-star), and as a Neo4j property graph. All three answered the same six engineering questions, at four sizes, and every answer was checked against an independent reference.

The use case

A fab building's utility chain, down to the SCADA tag

Switchgear feeds UPSs and PDUs, which power the production tools. Switchgear also powers the chillers, which cool the process-cooling-water (PCW) loops. Every tool has WinCC OA-style datapoints, and some datapoints carry alarms. Each feeds link carries seven engineering attributes. Those attributes are where the three models differ.

What I did, in order

The run, including what got in the way

S0

Checked the toolchain instead of trusting memory 2 blockers

RDF 1.2 is still a W3C Working Draft. pyoxigraph 0.5.13 parses triple terms, reifiers and annotations. The old RDF-star syntax << s p o >> :p o now loads as a reifier, so its meaning changes silently. Docker had no daemon and the Neo4j download site was blocked, so I ran Neo4j 5.26 (the final 5.x LTS) embedded from Maven Central with a Bolt port. The n10s plugin was unreachable.

S1

Generated one model-neutral dataset

Seeded and deterministic. One building gives 261 nodes and 398 edges, of which 138 feeds edges carry 7 properties each. Scales 10, 50 and 200 repeat the building.

S2

Plain RDF 1.1 in Oxigraph all correct

The class hierarchy answers "is this a production tool?" through rdfs:subClassOf*. SPARQL could not return a path, so I spelled out each depth with UNION branches. Q1 slowed in step with graph size, even though its answer never changed.

S3

RDF 1.2 triple terms and reifiers all correct

Q1 dropped to 0.3 ms at every scale. I showed two things a property graph can't hold: a claim that isn't asserted, and two independent sources about the same link (CMMS 0.83, WinCC OA 0.99).

S4

Neo4j property graph with Cypher all correct

shortestPath returns the chain natively. The planner turned [:FEEDS*] plus DISTINCT into a pruning BFS. "Production tool" works only because the loader set that label.

S5

RDF ⇄ property graph round trip, plus SHACL tool gap

The clean round trip was lossless (2,457 → 2,457 triples). Adding RDF 1.2-only provenance lost 6 triples. pyshacl caught exactly the 2 defects I injected, but rdflib 7.6 can't parse RDF 1.2, so validation ran on the RDF 1.1 copy.

S6

Bottlenecks

Counting paths in Cypher grew exponentially on a redundant mesh. A per-value write loop was 200× slower than batching. Q1's slowdown in plain RDF came from a bad join order, not from the n-ary pattern itself.

S7

Summary, runner, push

./run_all.sh reproduces everything. Each stage has its own commit on the session branch.

Refinement pass
R1

Checked how the real n10s handles RDF-star critical finding

Building the cloned n10s source was blocked by the session's permission policy, and I didn't work around it. Instead I read its source and ran its bundled parser (rdf4j 4.3.12). That parser rejects both RDF 1.2 syntaxes. It also creates an edge for every quoted triple, even one that isn't asserted. One phantom BIM edge hid a real single point of failure.

R2

Added Q6, a single-point-of-failure audit

Ignoring the medium edge property turns 30 at-risk tools into 0. Cypher filters each edge inside the path. SPARQL can't, so RDF needed a separate fab:feedsPower property built first.

R3

Tighter numbers

Each query now gets 1 warm-up and 15 runs, reported as p50 and p95. I added SCALE 200, durable on-disk writes in Oxigraph, and a relationship-property index test in Neo4j. The full run takes 1 min 43 s.

Median ms, log–log. The answer is the same 40 tools at every scale. RDF 1.1 "as written" grows with the whole graph. A traversal-first rewrite of the same query, or RDF 1.2's direct edge, stays flat. Neo4j times are client-side, Bolt round trip included.

Findings that change decisions

Six results worth repeating to a customer

30 → 0

Ignore one edge attribute, lose every SPOF

A single-point-of-failure audit that doesn't filter on medium = power treats cooling paths as power redundancy, and finds none of the 30 at-risk tools.

30 → 29

n10s turns a claim into an edge

An unasserted BIM claim ("this PDU also powers T-B01-107"), imported the way n10s 5.26 does it, became a real feeds edge. That faked redundancy and hid the tool at risk.

parse error

The bridge isn't RDF 1.2-ready

The parser bundled with n10s 5.26 (rdf4j 4.3.12) rejects <<( )>> and ~ {| |}. rdflib 7.6, which pyshacl depends on, fails too. Only the 2021 Turtle-star syntax imports.

2,700×

Model shape beats engine speed

The same impact query went from 802 ms (RDF 1.1, as written) to 0.3 ms (RDF 1.2 direct edge) on 500k triples. Rewriting the query alone gave 110×.

2.7 s

Redundancy makes paths explode

1M paths through a 20-tier 2N mesh. Reachability takes 2 ms. Never run an unbounded MATCH p=…-[*]->… on N+1 or 2N topologies.

140×

Batch your writes

Neo4j: 46k values/s batched vs 326/s with one transaction per value. Before the index finished building, batched writes ran at only 1.6k/s.

Decision guide

When to use which, and how they fit together

Plain RDF 1.1Use for integration
  • A shared asset model across BIM, CMMS, MES and SCADA
  • Standard ontologies: Brick, ISA-95, ECLASS, AAS
  • SHACL quality gates in pipelines
  • Most mature tooling
RDF 1.2Use for provenance
  • As-designed (BIM) vs as-operated (WinCC OA) reconciliation
  • Who asserted each link, when, and how confidently
  • Contradictory claims kept side by side
  • Check every tool in the chain first
Property graphUse for operations
  • Impact and root-cause analysis
  • Path and redundancy audits, GDS algorithms
  • Apps and dashboards built quickly in Cypher
  • Set labels deliberately: there's no ontology
Bottlenecks, each one hit for real

Where each model hits the wall

  1. Path explosion in Cypher on N+1 or 2N topologies. Use DISTINCT reachability, shortestPath, a depth bound, or GDS.
  2. SPARQL can't return a path. You unroll depths or post-process in code.
  3. Optimizer join order. Starting from every tool instead of the tripped switchgear cost 110×. Check query plans.
  4. Neo4j writes need batching and indexes that have finished building.
  5. RDF 1.2 tooling lag: rdflib, pyshacl and n10s 5.26 can't parse it. Oxigraph can.
  6. Label drift in an LPG: a label you forget to set gives a silent wrong answer in impact analysis.
  7. n10s phantom edges: a quoted triple becomes a real relationship, asserted or not.
  8. Property paths can't filter on edge metadata (RDF 1.1 or 1.2). Put attributes you traverse on into the predicate.
  9. Bolt result transfer dominates Neo4j client time for wide results. Aggregate on the server.
